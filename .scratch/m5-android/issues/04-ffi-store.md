# 04: Settings, history and secrets over FFI

**What to build:** `bolo-ffi` exposes the desktop's store on Android, so the settings app and the IME read and write the same `settings.toml` v2, history and keys.

**Blocked by:** 01

**Status:** done

- [x] `bolo-store` builds for Android: paths are injected (`Paths { config_dir, data_dir, models_dir }`) and don't come from `directories`; the Windows keyring store stays `cfg(windows)`.
- [x] `Bolo::new(paths, secret_store, listener)`. `SecretStore` is a foreign trait (`get`/`set`/`delete`) wrapped as a `keyring_core::CredentialStore` (ADR-0023). Kotlin implements it with a Keystore AES-GCM key and private SharedPreferences.
- [x] Settings over FFI as plain records: read, save (validated the same way as desktop's `form.rs`; share that code by moving it into `bolo-store` if it's platform-neutral), and an event when the file changes (the IME and settings activity both hold a `Bolo`).
- [x] `start_dictation(package_name, field)`: per-app resolution by package name (ADR-0022; `[[apps]]` rows match `exe` or `package`) and bundled Android defaults (`app_rules.toml` gains Android rows: WhatsApp, Gmail, Chrome, Keep, Messages, Slack). Sensitive fields → no recording, no history.
- [x] History: the journaling desktop does (text only, 30 days), list/search/delete/clear over FFI.
- [x] Tests: settings round-trip through the FFI records, package-name resolution, and secrets against keyring's mock store. Kotlin unit tests for the Keystore `SecretStore` run as an instrumented test on the emulator (`connectedDebugAndroidTest`, local only; CI runs the JVM tests).

## Outcome

- **Shared code went into `bolo-store`, not a new crate.** Three modules moved out of the desktop crate: `apps` (was `rules.rs`, with `app_rules.toml` now at `crates/bolo-store/app_rules.toml`), `form` (the platform-neutral part of `form.rs`: `General`, `AppChange`, `set_app`/`reset_app`/`add_app`, `new_exe`, `Changes`/`changes`, `CLOUD_ENGINES`) and `journal` (moved as is). Why: all three work on `Settings`, `AppProfile` and `History`, which `bolo-store` owns, and `bolo-ffi` already needs `bolo-store`. A new crate would sit on top of `bolo-store` with a single consumer pair and no independent dependency to justify it. The desktop crate keeps only Windows things: `rules.rs` is now a thin wrapper that adds the inserter's `Target` (the paste chord, multi-line swap safety) to `bolo_store::apps::Resolved`, and its `Form` flattens the shared `General` (`#[serde(flatten)]`, so the window's JSON is unchanged) around the push-to-talk key, autostart, the microphone and updates. Desktop tests pass unchanged apart from `f.general.*` paths in the form tests and one count in the Apps-tab test (the table now also has Android rows).
- **Paths are injected.** `bolo_store::Paths { config_dir, data_dir, models_dir }` with `settings_file()`/`history_file()`. `Paths::desktop()`, `config_dir()`, `data_local_dir()`, `Settings::default_path()` and `History::default_path()` (the `directories`-based helpers) are `cfg(not(target_os = "android"))`, and `directories` is a non-Android dependency. The Windows keyring store stays `cfg(windows)`.
- **App matching: an additive `package` key on `[[apps]]` rows**, no settings version bump. `AppProfile.exe` became `#[serde(default, skip_serializing_if = "String::is_empty")]` and gained `package: Option<String>`. A row matches the desktop app named by `exe` (tidied by `exe_name`) or the Android app named by `package` (trimmed, lower-cased by `package_name`); a row naming both matches either. Every v2 file written so far loads and saves byte-for-byte the same (tested). Resolution takes an `AppKey::{Exe, Package}`: exe keys keep the browser/title logic, package keys never match exe rules or exe rows and vice versa. `app_rules.toml` rules gained a `package` list; the Android rows are WhatsApp (+ Business), Gmail, Chrome, Keep, Messages (plain) and Slack (Markdown); none turns polish off. A package that no rule names gets the package's last part as its name (`com.example.notes` → "notes").
  - Caveat: a desktop Bolo older than this change would reject a package-only row (its `exe` was required) and treat the whole file as bad. The files never move between a phone and a PC, so this doesn't happen in practice.
- **Secrets.** `bolo_ffi::SecretStore` (`get`/`set`/`delete`, `delete` returns whether there was a value; errors are `SecretException.Failed(detail)`) is wrapped by `secrets::ForeignStore::wrap` as a `keyring_core::CredentialStore`; entries are `"<service>/<user>"` (`bolo/deepgram`). Kotlin's `KeystoreSecretStore` uses an AES-256-GCM key (alias `bolo-secrets`, no user auth, random IV per write) and stores base64(iv ‖ ciphertext) in private SharedPreferences `bolo_secrets`, with the entry name as GCM associated data so a value moved to another name doesn't decrypt. Exception messages name only the operation and exception type.
- **FFI surface.** `Bolo::new(paths: BoloPaths, secret_store, listener)` replaces `BoloConfig`. The engine config comes from `settings.toml` + the keys, with `models_dir` from `BoloPaths` (the settings' own `models_dir` is the desktop's) and Android's budgets (`idle_unload_secs = 20`, `mic_warm_secs = 30`). New calls: `settings()`, `save_settings(BoloSettings) -> BoloSettings` (tidied by `General::apply`; app rows checked by `AppChange::tidy` and `form::new_package`; bad values → `FfiException.Invalid`), `reload_settings()`, `apps()` (the Apps page entries), `set_api_key`/`api_key_hint`, `history(limit)`, `search_history`, `delete_history`, `clear_history`. `start(package_name, field: FieldKind)` returns a `DictationTarget { app_name, format, polish }`; `FieldKind.PASSWORD`/`INCOGNITO` are refused with `FfiException.SensitiveField` before the mic opens. `BoloListener` gained `on_settings_changed`.
- **Settings changes across `Bolo`s.** Every `Bolo` registers in a process-wide list; a save writes the file once and every `Bolo` on that file adopts it (engine `update_config` only when the engine part changed, `set_snippets` for snippets, history switch/prune) and calls `on_settings_changed`. A key set through one `Bolo` makes all of them re-read the keys. `reload_settings()` compares the file's modification time, for a write from another process (the keyboard can call it in `onStartInputView`). Android never warms the model on a settings change (`Changes::warm` is ignored, ADR-0022).
- **Journaling.** `on_final` writes the history row (package, language, engine, text), `on_polished` adds the polished text with outcome `delivered` (whether the keyboard managed to replace it is ticket 06's to record), `on_usage` feeds the usage meter. History is pruned at open and at most daily on a finished dictation, with the settings' retention (30 days by default).
- **Debug screen.** `MainActivity` opens one `Bolo` with `filesDir` / `noBackupFilesDir/models` and `KeystoreSecretStore`; the engine field (and the replay's `--es engine`) writes the settings' engine chain.
- **Tests.** bolo-store: the desktop and Android tables, package rows field by field, exe/package isolation, Android Apps rows, additive `package` loading, the shared form. bolo-ffi: settings round trip through the records and the file, desktop rows and unknown keys kept by an Android save, app-row tidying and errors, secrets through `ForeignStore` against a `SecretStore` backed by keyring's mock store (round trip, blank deletes, failures without values), and fake-STT dictations through `Bolo` for journaling, sensitive fields, package resolution, history search/delete/clear/off, cross-`Bolo` settings events and reload. Kotlin: `KeystoreSecretStoreTest` (instrumented, its own alias and prefs file) for round trip, encryption + AAD binding, and a `Bolo` reading keys through the store.
